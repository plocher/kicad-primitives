# ADR 0006: 1.0 capability and releasability bar

Date: 2026-10-24

Status: Accepted by the owner on 2026-10-24.

Ticket: [1.0 capability and releasability bar](https://github.com/plocher/kicad-primitives/issues/22)

Research input: [lift inventory](../review/lift-inventory-2026-10-24.md) ([Research: per-module lift inventory from donor repos](https://github.com/plocher/kicad-primitives/issues/9), PR #23).

## Problem

ADR 0005 locks the production dependency rule: donors may pin `kicad-primitives` only at `1.0.0` on public PyPI. It does not define what that version must contain.

Without an explicit bar, maintainers drift toward three bad defaults:

1. Treat the first symbol-library slice (ADR 0004) as if it were releasability.
2. Treat donor micro-task surfaces as the package API shape.
3. Delay `1.0.0` until full estate parity and consumer cutovers, or ship a hodge-podge of lifted fragments.

No current client is blocked on this package. Cutover theater is not the driver. The package still needs a coherent, robust, usable 1.0 minimum—not a finish line for all KiCad work.

## Constraints and requirements

- ADR 0001–0005 remain in force. Do not reopen distribution, TOC ownership, or the write model here.
- ADR 0002: parity means **used** capabilities; completeness and reliability may demand more; the owner locks the release bar.
- Public services describe **macro** KiCad work. Donor code is evidence and a floor. Donor APIs may be incomplete, buggy, or shaped for one slice; they are not the service contract.
- Package delivery does not wait on consumer cutovers (ADR 0005).
- Preserve ADR 0003 source-preserving writes and operation-specific verification. Do not substitute a CI or test-framework epic for functional capability.
- The lift inventory is catalogue evidence. Owner domain knowledge may amend usage where the catalogue under-counts (FieldUnit schematic geometry; symbol authoring).
- 3D models remain out of scope until requested (ADR 0002).
- KiCad IPC / in-process plugin Python is the wrong runtime for this package’s default path.

## Definition of success

A maintainer can answer:

1. What job does `1.0.0` perform?
2. How do surface design (A), proven implementation (B), and donor-used checks (C) relate?
3. Which services must be proven cores, at what depth?
4. What evidence declares the bar met?
5. What is deliberately deferred without calling it an exclusion from intended scope?
6. What does **not** gate the version number (cutover, offer issues, release automation)?

## Candidates and evaluation

### A: Foundation-only 1.0

Ship a small dependable surface (symbols plus thin extras). Donors may pin, but most workflows still need local I/O beside the package.

Pros: faster tag; low delivery risk.

Cons: little value while no client is blocked; weak meaning for ADR 0005’s production pin; invites a permanent dual stack.

Rejected as the whole bar.

### B: First-cutover 1.0

Require enough capability that one named donor can remove-and-replace a coherent I/O stack, with recipes.

Pros: proves migration is possible.

Cons: about 2× work (package plus consumer) for 1× package result; still a minimum shaped by one consumer; couples releasability to cutover theater the estate does not need now.

Rejected as the defining goal. Cutover remains a later, decoupled action.

### C: Estate used-capability parity only

Implement essentially every inventory **Used** row across ADR 0002 areas before `1.0.0`.

Pros: legally clear floor; matches “parity” language.

Cons: alone, it still permits donor-shaped fragments and micro-task APIs; misses “coherent, robust, usable package”; under-weights FieldUnit needs the catalogue marked unimplemented or historical.

Necessary as a **check**, not sufficient as the whole bar.

### D: Used floor plus macro service design and proven cores

Define complete functional surfaces for in-scope services (A). Implement proven cores so those services work in practice (B). Require donor-used paths to work through that surface (C), without letting C design the API. Amend the used floor with owner-known FieldUnit demand. Defer named 1.0 depth items (variants, geometry edit, and similar) without confusing them with standing exclusions or ownership boundaries.

Pros: matches the product goal; keeps donors as evidence; allows uneven depth; separates design completeness from implementation completeness; does not wait on cutovers.

Cons: larger than ADR 0004; requires ongoing surface catalogues and functional tests; defect ledger stays open-ended.

## Decision

Choose **D**.

`1.0.0` is the first public production release that meets this **capability and releasability bar**. It is a **minimum bar**, not the package finish line and not full general-KiCad completeness.

### A / B / C model

| Layer | Meaning |
| --- | --- |
| **A — Surface** | Define the complete functional contract for each in-scope service. The surface may be larger than, different from, or incompatible with donor APIs. This is the minimum design work for a macro service. |
| **B — Proven core** | Implement enough of that surface that the service is functionally real and works in practice—not a façade of stubs. Public areas at 1.0 **reflect B**: ship services that are proven, not an empty TOC. |
| **C — Donor floor** | Paths that donors **use** must be possible through the package surface. C is a **usability reflection**, not the only success metric and not the shape of the API. |

Unimplemented parts of A fail **explicitly** (unsupported operation) before making changes. They do not erase the need for a complete **definition**.

### What 1.0 is not

- Not “ADR 0004 symbols only.”
- Not “lift every donor module as-is.”
- Not “one consumer migrated.”
- Not “every KiCad operation implemented.”
- Not a claim that pre-1.0 labels carry compatibility (ADR 0005).

### Mandatory proven-core spine (B)

Depth is uneven. Each row is a proven core, not a promise of EESchema/Pcbnew editor parity.

**Projects**

- Discover and open project context; hierarchical schematic file list with **correct** sheet-path resolution; `text_variables`; write lock/guard hooks writers need.
- Sheet-walk defects in donors are **not** package policy. Correct hierarchy is part of B ([sheet-walk filing](https://github.com/plocher/kicad-primitives/issues/13) remains related work).

**Schematics**

- **Merged** placed-symbol read: fields, identity, transform, and related instance facts—one view, not three partial donor readers.
- **Geometry and electrical structure read** for FieldUnit-style workflows: curated symbols on a rigid grid; wires, junctions, labels, no-connects, sheet hierarchy edges; positions and layout relationships enough to **ingest and re-express** trackplans (SVG, model boards, panel reconstruction, and similar). This is owner-amended demand beyond the lift catalogue’s “unimplemented model” label.
- **Localized field annotate/repair** under ADR 0003—not whole-file `sexpdata.dumps` rewrite.
- Selected embedded `lib_symbols` restore-from-parent remains on the used spine (kDoctor); general cache sync stays bounded by A.
- Geometry **edit** is not forced into 1.0 B by the ingest use case; it may appear on A as defined/unsupported until a write workflow demands it.
- ERC belongs with project/schematic checks (see reports below).

**Symbol libraries**

- Full **A** for symbol and library manipulation in a KiCad context.
- **B** beyond ADR 0004: inspect with correct units, extends, and pins; property insert/update/delete; pin add/edit/remove; symbol create, rename, delete; copy/duplicate (including across libraries once resolution exists); preserve unit/body identity.
- Harvest FieldUnit-Subdivision / Railroad authoring experience, including **graphics-related** recipe and hand-finish lessons. Improve on mechanical “copy whole body into every unit” debt; do not copy Railroad policy into the package.
- Graphics **B** is real when authoring workflows can create and adjust the structures those harvests needed—not when every symbol-editor primitive has full interactive parity. Concrete outcome anchors when that work is ticketed: **unit-0 shared body**, **pin placement**, **body text**, and **SVG / contact-sheet inspection**. Full artwork-editor parity beyond those anchors is a deferral (below), not a silent hole in A.

**Library tables and resolution**

- One service: discover, read, resolve, and **write** global/project symbol and footprint tables.
- **KiCad-aligned** precedence and variable expansion (config home, nested tables, project shadowing, `${VAR}` from KiCad environment and project overrides). No hard-coded Mac-only `${KICAD10_*}` model as the contract; KiCad’s effective behavior wins on documented edges.
- Writes include add, remove, and rename of nicknames/entries under source-preserving rules appropriate to table files.
- `design_block` tables: on A; thin/optional in B unless promoted later.

**Connectivity**

- **A** states project-owned obtain/inspect/trace/compare, and the role of exchange datasets.
- **B** includes netlist **exchange** parse and the obtain/export capability compilers and verification need.
- A netlist file is **not** by itself the full public Connectivity area (ADR 0002).

**PCBs**

- Read footprints/pads/title and related BOM/fab metadata.
- DRC reports.
- **PCB fab exports** jBOM-style flows need: **gerbers and drills**. CPL and BOM **file generation** remain consumer product logic (jBOM), not this package.
- Board geometry editing is not 1.0 B.

**Footprint libraries**

- Read/identity/list/pad summary and lineage-style compare inputs once resolution can locate `.pretty` trees.
- Full `.kicad_mod` definition editor is not forced by C into 1.0 B; keep on A as deferred depth.

### Report and export capabilities (service surface, not a public CLI)

These operations belong on the relevant project/document/library services:

- Netlist obtain/export
- ERC and DRC reports
- SVG (and similar) exports used for symbol/schematic checks and FieldUnit-style rendering pipelines
- PCB gerber/drill exports as above

**Backend choice** (`kicad-cli`, reimplementation, or later mechanism) is an **implementation detail**, not the bar. `kicad-cli` may be used in 1.0 despite baggage and limits. **KiCad IPC / plugin-only Python is out of scope** for the default package path.

Private locator and env policy are settled when the first external engine is wired (related map work such as [#12](https://github.com/plocher/kicad-primitives/issues/12))—just in time, not as a universal pre-bar epic. There is no public `cli` module (ADR 0002).

### Defect and debt ledger (starting blockers)

Do not re-inherit these as package policy. The list is a **start** and stays **open-ended**; new blockers join as work finds them.

1. Wrong sheet hierarchy path base and/or wrong KiCad 10 sheet tokens in donor walks.
2. Dual disagreeing symbol readers; silent property/pin/extends loss in remaining donor readers.
3. Whole-file schematic rewrite as write policy.
4. Multiple lib-table parsers and hard-coded environment expansion.
5. Multiple CLI locators and env names—when an external engine is used, one private integration story.
6. Treating netlist exchange as full Connectivity ownership (design error, not a one-line bugfix).

### Evidence required to declare the bar met

| Kind | Role |
| --- | --- |
| **Functional tests** | **Required.** Representative workflows per proven service (symbol authoring including harvested graphics cases; schematic ingest for reconstruction; project hierarchy; table resolve and table writes; netlist exchange; PCB read/DRC/fab export as in spine). Prefer real fixtures and lifted donor scenarios. |
| **ADR 0003 gates** | Byte preservation always; connectivity or intended electrical change verification when the edit class requires it. Mechanism may vary; the contract is not optional. |
| **Unit tests** | Support internals; not the releasability story alone. |
| **Validation probes** | Optional disposable install checks (ADR 0005). **Not** a substitute for package functional tests. **Not** production migration. |

Do not build a greenfield behave/CI cathedral before foundation. Add functional scenarios **with** each slice; keep them explicit and table-driven when Gherkin lands.

### Explicit deferrals (intended scope, not 1.0 depth)

These remain in the package’s intended story where ADR 0002 already allows them. They are **not** 1.0 proven-core requirements. Promote later without reopening this bar’s A/B/C model:

- KiCad **variants** (project/export variant selection)—**future**
- PCB geometry editing
- Schematic **geometry edit** (read/ingest is in B; write of wires/labels/structure waits on demand)
- Live connectivity without export as a 1.0 must-have
- `design_block` tables as a polished product API
- Full symbol **artwork-editor** parity beyond the graphics B anchors above (unit-0 shared body, pin placement, body text, SVG/contact-sheet inspection)
- Footprint library **definition editing** beyond read/identity/lineage inputs

Per-service **operation catalogues** that detail every A method are follow-on design work under this ADR. They do not block recording this bar.

### Standing exclusions and ownership boundaries (not 1.0 deferrals)

These are existing scope or ownership decisions. Listing them here does **not** reopen them or reclassify them as “unimplemented depth”:

- **3D models** — out of scope until requested (ADR 0002)
- **Public `cli` module** — KiCad execution stays internal; report/export capabilities live on services (ADR 0002)
- **KiCad IPC / in-process plugin Python** as the default package backend — wrong runtime; not the default path
- **Consumer product logic** — fab orchestration, CPL/BOM **file generation**, railroad/domain compilers, and similar product workflows stay in consumers (jBOM, FieldUnit, Railroad, …). This package may supply the KiCad I/O those products need (for example gerber/drill export), not the product files themselves

Backend choice among allowed mechanisms (`kicad-cli`, reimplementation, and later options that are not IPC-default) remains an implementation detail under the report/export surface above.

### Non-gates for the version number

- Completed donor cutover
- Filed consumer “offer” migration issue
- Release-automation or full CI matrix epics
- Claiming the bar is already met today (ADR 0004 is foundation evidence only)

After `1.0.0`, normal SemVer applies (ADR 0005). First public production publish remains a separate release action when this bar is met.

### Relationship to ADR 0004

ADR 0004 remains the first shipped slice and a foundation proof. It is **not** the 1.0 completeness or releasability bar. Symbol-library 1.0 B **extends** that slice under this decision.

## Consequences

- Implementation proceeds as ordinary bounded slices under ADRs 0001–0006, with donor tests moved or rewritten as gates.
- Map ticket #22 is satisfied by accepting this ADR; it does not ship the capabilities.
- Subsequent work may add per-area surface catalogues, defect-ledger updates, and implementation issues without reopening the A/B/C philosophy.
- Consumer offer order and migration recipes remain decoupled (see map / future offer work). Optional probes may draft recipes early; they do not pin donors before 1.0.
- AGENTS.md and glossary terms should cite this ADR for releasability meaning.
- The lift inventory is not rewritten; owner amendments in this ADR supersede catalogue under-counts where they conflict for bar purposes.
